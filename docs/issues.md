# 已知问题 / 待测项

## RX-1：三个接收芯片中两个频繁丢包（未定位）

- 现象（用户此前测试，2026-10-12 记录）：3 个接收端 ESP32-C6 中，一个接收比较稳定，
  另外两个经常出现频繁丢包。
- 怀疑与硬件有关，尚未验证。具体是哪两个 COM 口：**待记录**。
- 之前的固件配置已丢失；当前固件为重新从官方 demo 复制的版本，丢包现象需要用新固件重新复现。

待排查方向（未验证，仅作为假设）：

1. 硬件：天线/匹配/FPC 连接、共晶振分配后的负载与幅度、各芯片供电与去耦。
2. 输出通路：官方 csi_recv 的主控制台是 UART0（GPIO16/17，921600），
   USB-Serial-JTAG 只是 secondary console；CSI 行通过 `ets_printf` 打印。
   经 USB hub 走 USB-Serial-JTAG 时，主机端读取不及时可能导致输出丢失，
   表现会像"丢包"。需要区分是**空中丢帧**（看 CSI 行里的 seq / rx_seq 是否跳号）
   还是**串口/USB 输出丢失**（行不完整、格式断裂）。
3. 同频干扰 / 三根天线相距 λ/2 的互耦。

现在可以直接用 `tools/csi_frame.py` 区分：`local_drop`（设备队列满 / USB 传输出错，配合 `crc_err`）
与 `air_loss`（`tx_seq` 跳号，空中丢失）。

建议的复现方式：同一发射端、固定信道，三路同时记录，看每路的 `air_loss` / `local_drop`；
然后交换 USB 口/hub 端口，看丢包是否跟着芯片走还是跟着端口走。

### 2026-10-12 首轮测量（新固件，HE20，信道 1，US，TX 100 Hz，台架近距离）

`tools/loss_test.py`，三路同时记录，结果保存在 `runs/`：

| 运行 | COM15 (4D:04) | COM17 (5D:68) | COM16 (07:C4) | 三路同时收到 |
|---|---|---|---|---|
| 30 s（TX 实际 91 Hz，修复前） | 0.37% | **2.30%** | 0.15% | 97.18% |
| 120 s（TX 100.0 Hz） | 0.15% | 0.17% | **1.28%** | 98.48% |

- 所有丢包都是 `air_loss`；`local_drop` = 0、`crc_err` = 0 → USB/串口输出这一段是干净的，
  旧固件下看到的"丢包"不能排除是字符串输出造成的，新固件下这条路径已排除。
- 两次运行最差的芯片不同（COM17 → COM16），目前**没有**看到"固定两颗芯片频繁丢包"的现象。
  样本还太少，需要更长时间、多次重复。
- 有若干秒三路同时下降（如 120 s 运行的 t=13/72/96/120），更像发射端或同频干扰事件，不是单颗芯片的问题。
- RSSI：COM15 约 −46 dBm，COM17 约 −30，COM16 约 −34（台架距离很近）。
